# AxiPortal BFF – Architecture, Hosting & Deployment Guide

---

## 1. Architecture Overview

```
Browser (HTML / CSS / JS)
        │
        │  same origin  /api/auth/*   →  all calls go here
        │  session cookie (HttpOnly, Secure, SameSite=Strict)
        ▼
┌───────────────────────────────────────────────────────┐
│               AxiPortal.BFF  (ASP.NET Core 8)         │
│                                                       │
│  wwwroot/          ← your portal HTML/CSS/JS          │
│  /api/auth/*       ← BFF proxy endpoints              │
│  /api/health/*     ← liveness + readiness probes      │
│                                                       │
│  Secrets in appsettings / environment variables       │
│  JWT token stored in server Session (Redis - never in JS)     │
│  Encrypted-secret cached in IMemoryCache              │
│  Retry + circuit-breaker via Polly                    │
└─────────────────┬─────────────────────────────────────┘
                  │  server-to-server (secrets safe here)
                  │
                  ▼
            AxiClient Backend
        (your .NET Core published)
```

The browser **never** talks directly to AxiClient.
It only calls `/api/auth/*` on the BFF, which lives on the same origin as your HTML.

### Production – Environment Variables (recommended)
ASP.NET Core maps `__` (double underscore) to config sections automatically:
```bash
Axi__ArmApiUrl=https://arm.yourcompany.com
Axi__AxiClientApiUrl=https://axiclient.yourcompany.com
Axi__SchemaName=YourSchemaName
Axi__Secrets__CreateAccount=your-production-secret
Axi__Secrets__AccountCheck=your-production-secret
Axi__Secrets__AccountDetails=your-production-secret
Axi__Secrets__CreateUser=your-production-secret
```

### Production – Azure Key Vault (enterprise)
```csharp
// Add to Program.cs before builder.Build()
builder.Configuration.AddAzureKeyVault(
    new Uri("https://your-keyvault.vault.azure.net/"),
    new DefaultAzureCredential());
```
Key Vault secret names use `--` as separator: `Axi--Secrets--CreateAccount`.

## 5. Hosting Options

### Option A: Single Host – IIS (simplest, Windows)

Your portal HTML and the BFF API are served from the same IIS site on the same domain.
No CORS needed. Session cookies work without any extra config.

```
IIS Site: portal.yourcompany.com
  └── Physical path: C:\inetpub\wwwroot\AxiPortal
       └── Published BFF output (dotnet publish -o .\publish)
            ├── AxiPortal.BFF.exe
            ├── appsettings.json
            └── wwwroot\
                 ├── index.html
                 └── auth.js
```

**web.config** (auto-generated by `dotnet publish`, just verify):
```xml
<configuration>
  <system.webServer>
    <handlers>
      <add name="aspNetCore" path="*" verb="*"
           modules="AspNetCoreModuleV2" resourceType="Unspecified" />
    </handlers>
    <aspNetCore processPath="dotnet"
                arguments=".\AxiPortal.BFF.dll"
                stdoutLogEnabled="true"
                stdoutLogFile=".\logs\stdout"
                hostingModel="inprocess" />
  </system.webServer>
</configuration>
```

Set environment variables in IIS → Site → Configuration Editor
→ `system.webServer/aspNetCore` → `environmentVariables`.

### Option B: Azure App Service (cloud)

```bash
# Publish
dotnet publish -c Release -o ./publish

# Deploy via CLI
az webapp deploy --resource-group rg-axiportal \
                 --name axiportal-bff \
                 --src-path ./publish.zip \
                 --type zip
```

Set secrets in: App Service → Configuration → Application settings:
```
Axi__ArmApiUrl          = https://arm.yourcompany.com
Axi__Secrets__CreateAccount = prod-secret
```

These appear as environment variables inside the container — ASP.NET Core reads them automatically.

### Option C: Docker / Container

```dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
WORKDIR /app
EXPOSE 8080

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish

FROM base AS final
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "AxiPortal.BFF.dll"]
```

Pass secrets via `docker run -e`:
```bash
docker run -p 8080:8080 \
  -e Axi__ArmApiUrl=https://arm.yourcompany.com \
  -e Axi__Secrets__CreateAccount=prod-secret \
  axiportal-bff
```

## 6. What Stays Separate vs What's Together

```
BEFORE (what you had):
  portal.yourcompany.com    → IIS serving static HTML/JS
  api.yourcompany.com       → .NET Core backend APIs
  (secrets in auth.js!)

AFTER (what you have now):
  portal.yourcompany.com    → AxiPortal.BFF (serves HTML + proxies APIs)
  api.yourcompany.com       → .NET Core backend APIs (untouched, no changes)
```

Your existing backend APIs are **completely unchanged**.
The BFF just sits in front of your portal and proxies calls server-to-server.

## 7. Development Quickstart

```bash
# 1. Clone / create the BFF project
cd AxiPortal.BFF

# 2. Restore packages
dotnet restore

# 3. Copy your portal files
cp -r ../your-portal/wwwroot/* ./wwwroot/

# 4. Update appsettings.Development.json with dev URLs + secrets

# 5. Run
dotnet run

# 6. Open browser
#    Portal:  https://localhost:5001
#    Swagger: https://localhost:5001/swagger
#    Health:  https://localhost:5001/api/health
```

## 8. Production Checklist

- [ ] All `Axi__*` secrets set via env vars or Key Vault (not in code)
- [ ] `Swagger:Enabled = false` in production
- [ ] `Cors:AllowedOrigins` locked to your actual domain
- [ ] Redis connection string set for distributed session (multi-instance)
- [ ] HTTPS enforced (`UseHsts`, `UseHttpsRedirection`)
- [ ] Rate limiting rules reviewed for your traffic patterns
- [ ] Health check endpoint monitored by your load balancer
- [ ] Logs flowing to your log aggregator (Serilog sink)
- [ ] `dotnet publish -c Release` (not Debug)
