# IIS Deployment Using ASP.NET Core `wwwroot`

This guide deploys the React site and ASP.NET Core BFF as one IIS application. React is compiled to static files and copied into the BFF's `wwwroot`; ASP.NET Core serves those files, the `/api/*` controllers, and the SPA fallback.

The supported production shape is:

```text
https://portal.example.com/AxiPortal/
https://portal.example.com/AxiPortal/api/*
```

Do not expose the Vite development server in production.

## 1. Repository Layout

| Path | Purpose |
| --- | --- |
| `Axi_3d_Website/` | React 19, TypeScript, and Vite application |
| `Axi_3d_Website/client/src/` | React source code |
| `Axi_3d_Website/dist/public/` | Vite production output |
| `AxiPortal 3/` | .NET 8 BFF |
| `AxiPortal 3/wwwroot/` | Static files served by the BFF |
| `AxiPortal 3/axiglobalconfig.json` | Runtime and upstream service configuration |

The final publish directory must contain the React `index.html` at `wwwroot/index.html`.

## 2. Prerequisites

Install or confirm the following on the deployment server:

- Windows Server with IIS and the Static Content feature.
- The .NET 8 ASP.NET Core Hosting Bundle, matching the deployed runtime.
- Node.js and pnpm on the build machine. Node/pnpm are not required on the IIS server.
- Network access from the BFF server to Redis and configured upstream Axi services.
- A DNS record and an HTTPS certificate for the portal hostname.
- An account or application-pool identity with write access only to the configured log directory.

Enable IIS features from **Server Manager > Add Roles and Features > Web Server (IIS)**. Do not grant the application pool write access to the entire publish directory.

## 3. Production Configuration

Choose the IIS application alias before building the frontend. The examples below use `AxiPortal`.

Set the React base path from `Axi_3d_Website`:

```powershell
$env:VITE_APP_BASE_PATH = "/AxiPortal/"
```

`VITE_BFF_ORIGIN` is a Vite development-proxy setting. It is not required for this deployment because the browser calls the same-origin `/AxiPortal/api/*` endpoints.

Prepare a production `AxiPortal 3/axiglobalconfig.json` with the correct values for:

- Redis and Axpert Redis connectivity.
- Axi upstream service URLs and credentials.
- Google, Microsoft, and Supabase OAuth settings.
- Logging directory, retention, and file-size limits.
- Rate-limiting and CORS settings.

Keep secrets out of the React build. Anything placed in a `VITE_*` variable is visible in the browser bundle. Store server secrets in protected configuration or IIS environment variables, and restrict ACLs on `axiglobalconfig.json`.

OAuth callback URLs, cookie domain/path, and allowed origins must use the final HTTPS hostname and `/AxiPortal` path. Verify that production cookies are `HttpOnly`, `Secure`, and have the intended `SameSite` policy.

## 4. Build the React Site

From the repository root:

```powershell
Set-Location .\Axi_3d_Website
pnpm.cmd install --frozen-lockfile
$env:VITE_APP_BASE_PATH = "/AxiPortal/"
pnpm.cmd check
pnpm.cmd build
```

The build writes static files to:

```text
Axi_3d_Website/dist/public/
```

Before continuing, confirm that the directory contains `index.html`, JavaScript chunks, CSS, and the referenced `assets/` files. Do not copy `client/` or `node_modules/` to IIS.

## 5. Prepare `wwwroot`

Back up the currently deployed static files before replacing them:

```powershell
$stamp = Get-Date -Format "yyyyMMdd-HHmmss"
Copy-Item "D:\inetpub\AxiPortal\wwwroot" "D:\backups\AxiPortal-wwwroot-$stamp" -Recurse
```

Copy the contents of `dist/public` into the BFF's `wwwroot` staging directory. Use a staging directory outside the live IIS path, then include that directory in the publish step. The result should be:

```text
AxiPortal 3/wwwroot/
├── index.html
├── assets/
└── other files emitted by Vite
```

Do not leave the old portal `index.html` or old JavaScript entry points beside the React build. Duplicate entry files can cause stale assets to be served.

## 6. Build and Publish the BFF

From the repository root:

```powershell
dotnet restore ".\AxiPortal 3\AxiPortal.BFF.csproj"
dotnet build ".\AxiPortal 3\AxiPortal.BFF.csproj" -c Release --no-restore
dotnet publish ".\AxiPortal 3\AxiPortal.BFF.csproj" `
  -c Release `
  --no-restore `
  -o "D:\releases\AxiPortal\current"
```

Validate the publish output:

```text
D:\releases\AxiPortal\current\
├── AxiPortal.BFF.exe
├── AxiPortal.BFF.dll
├── web.config
├── axiglobalconfig.json
└── wwwroot\
    ├── index.html
    └── assets\
```

Use the `web.config` generated by `dotnet publish`; it starts the ASP.NET Core process through IIS. Do not replace it with a static-file-only configuration.

## 7. Configure IIS

Create an IIS website or application with:

```text
Alias:          AxiPortal
Physical path:  D:\releases\AxiPortal\current
Application pool: AxiPortalPool
Managed runtime: No Managed Code
Pipeline:       Integrated
Enable 32-bit:  False (unless the deployment explicitly requires it)
```

Bind the site to HTTPS and configure the certificate. Redirect HTTP to HTTPS at IIS or at the application boundary. Ensure the IIS application is actually mounted at `/AxiPortal`; the alias must match `VITE_APP_BASE_PATH`.

Grant the IIS application-pool identity:

- Read and execute permission on the publish directory.
- Write/modify permission only on the configured log directory.
- Read permission on protected configuration files.

Recycle the application pool after deployment. If files are locked, stop the site or application pool before replacing the release directory, then start it again after copying.

## 8. Routing and Middleware Requirements

The BFF pipeline must retain this behavior:

1. HTTPS and security headers are applied.
2. `UseDefaultFiles()` and `UseStaticFiles()` serve React assets.
3. `MapControllers()` handles `/api/*` requests.
4. The fallback returns `wwwroot/index.html` for non-API React routes.
5. Unknown `/api/*` requests return an API 404, not the React HTML document.

Do not add a second IIS rewrite that sends `/api/*` to `index.html`. That masks backend routing errors and produces confusing JSON/HTML failures.

## 9. Deployment Procedure

1. Confirm the release branch and production configuration.
2. Run React type checking and build.
3. Copy the React output into the BFF `wwwroot` staging directory.
4. Run the Release BFF build and publish.
5. Back up the current IIS release.
6. Stop or take the IIS application offline.
7. Copy the complete publish output to the new release directory.
8. Confirm `wwwroot/index.html` and `web.config` exist.
9. Start the site and recycle the application pool.
10. Run the smoke tests below and inspect application logs.

Keep releases in timestamped directories and switch the IIS physical path between releases when possible. This makes rollback faster and avoids partially copied files.

## 10. Post-Deployment Verification

Check these URLs first:

```text
https://portal.example.com/AxiPortal/
https://portal.example.com/AxiPortal/api/health
https://portal.example.com/AxiPortal/api/oauth/config
```

Then verify in a private browser window:

- Refreshing `/AxiPortal/`, `/AxiPortal/packages/setup`, and other React routes returns the React page.
- Browser developer tools show JavaScript/CSS requests under `/AxiPortal/` with HTTP 200.
- `POST /AxiPortal/api/auth/check-send-otp` reaches the BFF and returns the expected envelope.
- Login, signup, OTP, SSO, schema selection, and logout work.
- The session cookie is present with the expected `HttpOnly`, `Secure`, `SameSite`, and `Path` attributes.
- Package confirmation does not queue until the user confirms.
- Package installation progress updates and stops after terminal states.
- Redirecting to the main AXI application uses the expected target URL.

Do not treat a successful React page load as a successful deployment until an API request and an authentication smoke test also pass.

## 11. Security Checklist

- Use HTTPS in every non-development environment.
- Never put Redis passwords, upstream credentials, OAuth secrets, or signing keys in React variables.
- Restrict access to `axiglobalconfig.json`, logs, and release directories.
- Disable IIS directory browsing.
- Keep the .NET 8 Hosting Bundle and Windows Server patched.
- Confirm security headers remain enabled after deployment.
- Restrict OAuth redirect URIs to the production hostname and path.
- Review CORS settings; same-origin hosting should not require permissive CORS.
- Redact tokens and secrets from application logs.
- Do not expose Swagger publicly unless it is explicitly protected.

## 12. Troubleshooting

### HTTP 500.30 or 500.31

Check that the .NET 8 Hosting Bundle is installed, the application-pool identity can read the publish directory, and `axiglobalconfig.json` is present beside the executable. Run the published executable from a maintenance console to see startup errors, and inspect the ASP.NET Core stdout log if enabled temporarily.

### React route returns 404 after refresh

Confirm the request is reaching the ASP.NET Core fallback, `wwwroot/index.html` exists, and the application is mounted at the same `/AxiPortal` path used during the Vite build.

### `/api/*` returns HTML or a React page

Inspect IIS rewrite rules and the BFF fallback. API requests must reach `MapControllers()` and must not be rewritten to `index.html`.

### Assets return 404

Check that `VITE_APP_BASE_PATH` ended with `/`, that the build was copied from `dist/public`, and that the browser requests use `/AxiPortal/assets/...`.

### Authentication or OAuth fails

Check HTTPS, cookie attributes, proxy headers, the configured public hostname, and OAuth callback URLs. Confirm the browser is calling `/AxiPortal/api/*` rather than a development host or `/api/*` at the domain root.

### Package progress does not update

Check BFF logs, Redis connectivity, the schema and username values sent to `package/progress`, and the configured polling interval. Verify the BFF can reach the installer/progress services from the IIS server.

## 13. Rollback

1. Stop the IIS application or recycle the application pool.
2. Point the IIS application to the previous timestamped release, or restore the backed-up `wwwroot` and BFF files.
3. Restore the matching production configuration if it changed.
4. Start the application and recycle the pool.
5. Run `/AxiPortal/api/health`, a login smoke test, and a React route refresh.
6. Preserve the failed release logs for diagnosis.

Do not roll back only the React `wwwroot` while keeping an incompatible BFF binary or configuration. Treat the published directory as one release unit.

- [ ] React `pnpm.cmd check` passes.
- [ ] React production build succeeds.
- [ ] `wwwroot/index.html` is the current React build.
- [ ] BFF Release build and publish succeed.
- [ ] Production configuration and secrets are present and protected.
- [ ] IIS Hosting Bundle and application-pool settings are correct.
- [ ] HTTPS binding and OAuth redirect URLs are correct.
- [ ] `/AxiPortal/api/health` responds successfully.
